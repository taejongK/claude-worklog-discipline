## 자동 문서화 규칙 (필수)

작업과 함께 문서를 갱신한다. 아래 상황에서는 **사용자가 요청하지 않아도 자동으로** 실행한다.
모든 작업 문서는 `docs/worklog/` 안에 둔다. 중심은 날짜별 로그이고, 상세 문서는 로그에서 링크로 연결한다.

```
docs/worklog/
  {YYYY_MM_DD}.md        날짜별 작업 로그 (하루 한 파일)
  details/               작업 단위의 상세 문서
  templates/             AGENTS 템플릿
```

### 작업 완료 시 (날짜별 로그) — 항상

```
0. 언제 기록하는가
   - 기록한다: 레포의 파일을 변경(생성·수정·삭제)한 작업이 일단락되어,
     사용자에게 결과를 보고하는 응답을 마치기 전.
   - 기록한다: 사용자가 "여기까지 기록해줘"처럼 기록을 요청한 시점. 파일 변경이 없는
     조사·논의라도 그 시점까지의 내용을 기록한다 (아래 제외 조건보다 우선한다).
   - 기록하지 않는다: 파일을 읽기만 한 조사·질의응답, 변경 없이 끝난 시도,
     worklog 문서 자체만 고친 경우, 사용자가 "기록 생략"이라고 한 경우.
   - 같은 작업이 여러 턴에 걸쳐 이어지면(후속 수정·피드백 반영) 새 항목을 만들지 말고
     그날의 기존 `###` 항목을 갱신한다. 목표가 다른 새 작업일 때만 새 항목을 만든다.

1. 작업이 끝나면 docs/worklog/{YYYY_MM_DD}.md (오늘 날짜) 에 기록한다.
   - 파일이 없으면 `## {YYYY_MM_DD}` 헤더로 새로 만든다.
   - 작업 단위는 `### {작업 제목}` 으로 파일 끝에 append 한다.

2. 독자는 코드를 모르거나 보지 않은 사람이다.
   이 항목만 읽고 "무슨 작업을, 왜, 어떻게 했고, 결과가 어땠는지" 알 수 있어야 한다.
   각 작업 항목에 반드시 포함:
   - 작업자: 이름 (모르면 사용자에게 물어본다)
   - 배경: 왜 이 작업이 필요했는지, 무엇을 달성하려 했는지 (목표)
   - 방법: 어떤 접근으로 풀었는지 — 코드 수준이 아니라 일의 흐름으로
   - 결과: 목표 대비 무엇이 달라졌는지, 어떻게 확인했고 확인 결과는 어땠는지, 남은 문제

3. 코드 변경점을 나열하지 않는다 (그건 git 이 기록한다).
   파일·함수명은 독자가 위치를 찾는 데 꼭 필요할 때만 최소한으로 쓴다.

4. 헤더는 `##`(날짜)와 `###`(작업)만 쓴다.
   항목 내부 구분은 별도 헤더 대신 위의 `라벨:` 불렛으로 가볍게 표현한다.
```

### 더 깊게 정리할 내용이 있을 때 (상세 문서)

```
작업 항목에 담기엔 긴 내용(설계 대안 비교, 디버깅 과정, 실험 결과, 조사 내용 등)은
docs/worklog/details/{YYYY_MM_DD}_{주제}.md 로 따로 만들고,
그날 로그의 해당 작업 항목에 링크를 남긴다:
  - 상세: [{주제}](details/{YYYY_MM_DD}_{주제}.md)
같은 주제를 이후 작업에서 이어가면 기존 상세 문서를 갱신하고, 그날 작업 항목에 다시 링크한다.
```

### 디렉터리 구조 변경 시 (AGENTS.md 계층)

```
새 디렉터리 추가/역할 변경 시 해당 디렉터리의 AGENTS.md 를 갱신한다.
- 상위 디렉터리 AGENTS.md 의 Subdirectories 표도 함께 갱신.
- <!-- MANUAL: --> 마커 아래 손으로 쓴 내용은 절대 덮어쓰지 않는다.
- 없으면 docs/worklog/templates/AGENTS_TEMPLATE.md 형식으로 새로 만든다.
```
